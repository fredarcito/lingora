# Multilingual interface (i18n)

Status as of 2026-10-29: Spanish and English included; any other language in `LANGS`
is generated on the machine with the local translation model.

Not to be confused with the **translation** languages (`LANGS` in
`src-tauri/src/config.rs`, 37 languages): this is about which language the
**interface** is shown in. They are independent: someone can use the interface
in Spanish and translate between French and Japanese.

## Why it is done this way

- **Small installer.** The 37 translation files are not shipped: only `es` and
  `en`. The rest is generated once with HY-MT2, which is already in the app (all
  local, no cloud; see CLAUDE.md §3).
- **No new dependencies.** It is an own module of ~150 lines instead of
  `react-i18next` (CLAUDE.md forbids adding packages without asking).
- **All in the frontend.** Generation uses the `translate` command that already
  existed and saves to `localStorage`. `src-tauri` was not touched (editing it
  restarts `tauri dev`). If it ever moves to a file on disk, a new command in Rust
  will be needed.

## Files

| File | What it does |
|---|---|
| `src/i18n/index.jsx` | Engine: `t()`, `useT()`, `useLang()`, `I18nProvider`, storage of generated languages. |
| `src/i18n/es/<ns>.json`, `src/i18n/en/<ns>.json` | Texts. One file per screen or module (the file name is the namespace). |
| `src/i18n/generate.js` | Translates `en` into another language with the local model. |
| `src/LanguagePicker.jsx` | Picker in Settings → Interface (included, generated, "Generate another language…"). |
| `src/LangOffer.jsx` | One-time notice at startup if the system is in a language that can be generated. |

## How to use it

- The JSON files are flat; the final key is `<file>.<key>`: `sidebar.json` with
  `"menu"` → `t("sidebar.menu")`.
- Variables with `{name}`: `t("settings.version", { version })`.
- Plurals: keys `key_one` / `key_other` and `t("key", { count: n })`
  (`Intl.PluralRules` picks the form; if it is missing, it falls back to `_other`).
- Language names: Rust sends them in Spanish. `App.jsx` passes the views
  `shownLanguages`, with the name in the interface language (`langName`, which
  uses `Intl.DisplayNames`). `languagesRef` keeps the ones from Rust: `start` uses it.
- In components: `const t = useT();` (re-renders when the language changes). Outside
  React (`notes.js`, `api.js`): `import { t } from "./i18n"`. Careful: that `t` does
  not re-render; it only works for texts that are computed when shown.
- Resolution: generated language → included language → **English** → the key itself.
  An untranslated key never leaves the screen empty.
- Module-level texts (constants with labels): store only the id and call `t()`
  when rendering. If you store the already translated text, it won't change when the
  language changes.

## Rule when adding or changing texts

1. Add the key **in `es/` and in `en/`** of the same file. Both must have exactly
   the same keys (suggested check: compare the key sets of each pair of files).
2. `en` is the **source for generation**: what gets translated into other languages
   is `en`. Write short, clear English; it is what the model will see.
3. Languages that were already generated don't know about it: the new keys appear in
   English until the user presses "Generate again" (pending idea: detect missing keys
   and translate only those).
4. Don't put model names in the texts (CLAUDE.md §3).

## Language detection

`navigator.language` reduced to the base code (`es-MX` → `es`). If it is `es`, Spanish;
otherwise, English. A language chosen by hand is saved in `lingora.uiLang` and takes
precedence over the system's. A saved value that no longer exists (deleted language)
is ignored.
Arabic, Hebrew, Persian and Urdu set `dir="rtl"` on `<html>`; the CSS has not
been reviewed for RTL.

The two windows (main and floating captions) share `localStorage`; the
`storage` event updates the other one when the language changes.

## How a language is generated (`generate.js`) and why

Translation is done **key by key**, from `en` into the language, with `local = true` (HY-MT2) and a
context note ("short interface text…"). Lessons learned while testing with
Italian; **don't undo them**:

- **The `{x}` placeholders are masked.** The model translates the names inside the
  braces (`{date}` → `{data}`). Before translating they are swapped for `{1}`, `{2}`…
  and restored afterwards. If placeholders are missing or extra, the key is discarded
  and stays in English. Since they are numbered, the model can reorder the words
  without changing which value goes in each slot.
- **The number of commas is not validated.** An earlier version did, and it discarded
  correct translations (commas change between languages; loose words were confused
  with lists).
- **Months don't go through the model.** `notesLib.months` is taken from
  `Intl.DateTimeFormat(code, { month: "short" })`: the model returned full names,
  not the abbreviations the interface needs.
- **The local server can hang.** A slow request times out after 30 s in Rust
  and `llama-server` is restarted; requests in that interval fail. That is why each
  key is retried once (with `translateWarmUp`) and at the end there is a review of the
  ones that stayed in English.
- **It is only sequential.** There is a single instance of `llama-server`; ~355 keys
  take a few minutes.
- Each discarded or failed key is logged with `console.warn("[i18n <code>] …")`
  with the reason: check the window's console (not the `tauri dev` terminal).

Storage: `lingora.uiStrings.<code>` = `{ strings, date, missing }`. If it
doesn't fit in `localStorage`, `saveGenerated` throws and the picker shows it as an
error.

## Pending

- **Texts that come from Rust in Spanish:** `title` and `detail` of the diagnostics
  (`doctor.rs`), errors (`error.rs`) and the exported note headings ("## Resumen" (Summary),
  "## Transcripción" (Transcript) in `notes.rs`). They need to be mapped by id/code and not by
  text. `Diagnostics.jsx` compares `c.fix === "Descargar"` with the text Rust sends:
  it should be an id.
- **Quality of automatic translation:** the output is somewhat literal ("Il linguaggio di
  Lingora è mostrato qui"). Ideas: a context note per key (`_ctx`) and a glossary
  (interface, translate, notes, settings).
- **New keys in languages that were already generated:** translate only the missing ones.
- **Fallback list** of `App.jsx` (`{ code: "es", name: "Español" … }`) with fixed
  names; it is only seen if loading the languages fails.
- **RTL:** review the CSS for Arabic and Hebrew.
- **Startup notice:** it only compares the base code, so `zh-TW` doesn't match codes
  like `zh-hant` in `LANGS`.
- **Time and quality of generation have not been measured** for languages with
  non-Latin scripts (Japanese, Arabic, Thai…).
